§1. Immutable 15 CA Registry (15子系統白名單)
[ANCHOR:MIP-V220-SEC1]
本章節確立 Spartoi-OMOC 系統中 不可變更 的 15 個核心子系統（Capability Areas, CAs）。此清單為 L2-ARCH 與 L1-SRS 的最高執行索引摘要，旨在解決《Spartoi-OMOC_MIP_v2.1.0_審查報告》中指出的「表格截斷」與「職責邊界模糊」問題。
治理原則 (Governance Rules)：
1. Stable ID Immutability：stable_id 為系統內部唯一主鍵，永久鎖定。
2. No 16th Subsystem：嚴禁新增第 16 個子系統；新功能必須歸納至既有 CA 之下。
3. One-Rule-One-Place：本表僅做索引映射，詳細實作邏輯外導至 ARCH 與 Pipeline 方案。
________________

1.3 Anti-Drift Rules (反漂移規則：禁增第16 CA)
[ANCHOR:MIP-V220-1-3-ANTIDRIFT]
為防止架構腐化與邊界模糊，本系統執行以下嚴格的「反漂移（Anti-Drift）」規則。任何違反此規則的變更請求（CR）將被視為 BLOCK_RELEASE。
   1. Fixed 15 CAs (數量鎖定)：

      * 系統子系統數量 固定為 15 個。嚴禁新增第 16 個子系統。
      * 已刪除/併入聲明：
      * CA-FIREWALL：已於 v6.0.0 架構決策中正式廢除，功能併入 CA-GOVERN。
      * CA-AGENT：已於 v6.0.0 架構決策中正式廢除，功能併入 CA-COLLAB。
      2. Immutable Stable IDs (ID 不可變)：

         * 表 1.1 中的 stable_id（如 CA-WRC）為系統內部唯一主鍵，永久不可變更。
         * 允許：修改 Display Name（顯示名稱）以適應 UI 需求（需更新 ICD Alias Registry）。
         * 禁止：修改 Stable ID 或 Macro Module 歸屬。
         3. Functionality Containment (功能收斂)：

            * 任何新功能必須歸納至既有的 15 個 CA 職責範圍內，不得因功能新增而創建新的頂層模組。
            * 案例：新增「情緒分析」功能應歸入 CA-TA（作為特徵）或 CA-CORPUS（作為標註），而非建立 CA-SENTIMENT。
            * 來源依據：[SRC:SRS v8.1.0 §1.2.1, 15CA BP v0.2.0 §0.4, MIP v2.0.0 Guide §2.1]

4.1.1 The "Engine vs. Contract" Rule (引擎與契約分離原則)

4.3 Integration & Constraints (整合與約束)
[ANCHOR:MIP-V220-4-3-CONSTRAINTS]
本節定義將上述工具整合至系統時，必須遵守的硬性約束。違反此處約束的實作，將在 Preflight 或 Gate 階段被 BLOCK_RELEASE。
4.3.1 Supply Chain Hardening (供應鏈硬化)
依據 SRS v8.1 §2.3.4 與 OMOC-MVU Skills Supply Chain，所有外部依賴必須「鎖定」：
            * Immutable Pinning：所有 GitHub Actions 引用 (uses:) 必須鎖定至 Full-Length Commit SHA (40-hex)，嚴禁使用浮動標籤（如 @v1, @latest）。
            * Gate Hook: GATE-SC-001-PINACT。
            * Dependency Lock：Python 套件必須使用 requirements.lock 或 poetry.lock 鎖定具體版本與 Hash。
            * Security Scan：所有 Workflow 變更必須通過 zizmor 掃描，高風險漏洞零容忍。
            * Gate Hook: GATE-SC-002-SUPPLYCHAIN。
4.3.2 No-Paid-API Constraint (非付費 API 約束)
依據 LBP-C(ADR) ADR-029 與 SRS v8.1 §2.3.5，核心流程必須遵守：
            * WebTools-NA：優先使用 Web 介面與剪貼簿（WT-NA）進行協作，禁止在核心管線（Pipeline A/B/C）中依賴按量計費的 LLM API（如 OpenAI API）。
            * Local Fallback：關鍵工具（如 Embedding、RAG Indexing）必須支援本地執行模式（如使用 Qdrant Local, DuckDB），確保在斷網或無 API 額度時仍可運作。
4.3.3 Adapter Pattern Requirement (適配器模式要求)
依據 Evidence Contract：
            * Wrapper Required：若工具原生輸出不符合 ICD 定義的 Schema（如 Backtesting.py 的 HTML 報告），必須編寫 Adapter (Wrapper) 將其轉換為標準 JSON 格式（如 backtest_report.json），並附帶原始報告作為 Artifact。
            * Determinism：工具執行必須具備可重現性（Reproducibility），必須在輸入中固定 Random Seed。

§6. Route-Out Register (外導註冊表)
[ANCHOR:MIP-V220-SEC6]
本章節依據 One-Rule-One-Place (單一法則落點) 原則，建立 MIP 作為「總路由表」的核心機制。MIP 本身不定義詳細規格、不撰寫操作步驟、不列舉 Schema 欄位，而是提供通往 SSOT (Single Source of Truth) 的精確路由指針。
治理規則 (Governance Rules)：
               1. Mandatory Routing (強制外導)：凡涉及「如何做 (HOW)」、「規格細節 (SPEC)」、「數值門檻 (LIMIT)」之內容，必須 透過本註冊表轉址至 L1~L6 之權威文件。
               2. Precise Anchoring (精確錨點)：解決 Audit Report A (CRIT-005) 與 Audit Report B (CR-MIP-004) 指出的「空指標/弱定位」問題，所有外導必須包含目標文件 ID 與目標錨點（Anchor）。
